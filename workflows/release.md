# Проверка готовности и публикация — разные действия

`hook run --case ID --spec FILE --expected-revision R` выполняет явную проверку,
сохраняет результат и причины блокировки. Сам hook ничего не публикует.

Спецификация: `event=pre-release`, непустые `procedure_id`, `procedure_version`,
`basis_refs` с точными текущими refs. Для каждого target нужен чистый отдельный
review на эту ревизию; активные P1/P2, отзыв оснований и устаревшие targets блокируют.

- `release_scope=strategy` (по умолчанию): требуется действующий confirmed DEC,
  который связывает эти точные стратегии с реальным бизнес-согласием; pending H
  не проходит. Fixture approval не является реальным согласием.
- `release_scope=materials`: дополнительно `approval_ref` на текущий real publication
  APR с точно теми же targets и `destination`, совпадающим с terms.destination.
  Это разрешение на конкретные материалы, не подтверждение полезности стратегии.
  Правообладатель проверяет состав immutable proposal до APR; последующий upload
  должен сверить реальные bytes с proposal. Hook сам не проверяет байты GitHub.
- `release_scope=contest_submission`: hook явно сообщает, что юридическая отправка
  не подтверждена. Нужны проверка применимого брифа, площадки, прав и отдельное
  действие капитана с receipt. Publication APR не заменяет юридическую отправку.

Read-only status и config/gates.json — диагностика/исходные запреты установки,
не независимые человеческие согласования и не динамическая история кейса.
Файлы config не наследуют согласования автора. Не снимать их блокировки просто
ради зелёного статуса. Технические тесты policy doubles не доказывают реальные H.
